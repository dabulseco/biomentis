Learning tool

Biomentis isn't just an agent — it's a teaching assistant

The 85-step nanobody pipeline and 52-step LAMP primer run on the agent capability page are exactly the kind of dense, interdisciplinary workflow that's hard for a student to follow — lots of tools, lots of domain vocabulary, lots of "why did it just do that?" Biomentis has an opt-in instructional layer built specifically to make runs like those legible, step by step, without changing what the agent actually does.

Opt-in — disabled by default, zero behavior change for research use
How it works

Every agent step becomes a graded teaching moment

1

Grounded in the student's own materials

Instructors or students upload course PDFs, slide decks, or URLs. Files are chunked, embedded locally (all-MiniLM-L6-v2), and indexed in a per-session Chroma vector store — no data leaves the machine to build the knowledge base.

2

A teaching card for every step

After every reasoning, code, observation, solution, summary, or file event the agent emits, the tutor generates a card: what the step is doing, why it exists in the workflow, prerequisites the student should already know, and what to look for in the output.

3

Bloom's & Webb's DOK tagging

Every card and every chat answer is tagged with a target Bloom's taxonomy level (Remember→Create) and Webb's Depth-of-Knowledge level (1–4), calibrated by event type and shaped by whatever rubric the instructor supplies.

4

Strict citation whitelisting

Both the teaching cards and the tutor chat are told to cite only retrieved knowledge-base snippets, never invent a source. A validator drops any citation that isn't in the retrieved set before it's ever shown to the student.

5

A chat column grounded in the same KB

Students can ask follow-up questions at any point. Every answer is classified against the rubric and logged alongside its Bloom/DOK level and which rubric objectives it hit.

6

A gradable, exportable record

Every step and every Q&A exchange is appended to a per-session JSONL log, exportable as JSON or two CSVs (steps, Q&A) — ready for grading or an LRS import.

Applied to a real run

What this would look like on the nanobody pipeline

The 85-step CHIKV nanobody trace on the agent capability page ran with the tutor disabled — it's a research-mode session, and that's exactly the point: nothing about the agent changes when the tutor is off. With it enabled, each of those 85 steps would pause and surface a card. Step 4, for example — a code cell running query_pdb against the CHIKV E1–E2 trimer — would generate a card explaining what a PDB query does, why the pipeline needs a structural template before it can dock anything, what prerequisite knowledge (protein structure file formats, resolution/quality filtering) a student should already have, and what a "good" result looks like — citing whichever course reading the instructor uploaded on structural biology databases.

The esm import error the agent hit mid-run (see the friction callout on the nanobody case study) is itself a teachable moment under this model — a card explaining what a missing dependency means and why the agent's recovery path was reasonable, rather than something to edit out of the record.

Example classroom workflow

Pre-class, in-class, post-class, iterate

Pre-class

The instructor uploads a few course PDFs (or points the KB at the textbook's online chapters) and uploads a custom YAML rubric mapping the day's learning objectives to Bloom/DOK levels. Each student gets their own session, but the rubric can be reused.

In-class

Each student runs a small task — e.g. "Find 3 candidate nanobodies against CHIKV E2." The agent runs to completion; the student reads each teaching card at their own pace, clicks Continue, and asks follow-up questions in the chat column.

Post-class

The student exports their session log and submits it. The instructor reads each step's instruction.why to see what the student was supposed to learn, scores the Q&A records against the rubric using their Bloom/DOK tags and rubric_hit ids, and aggregates across students by session id to spot common sticking points.

Iterate

The instructor updates the rubric for next week based on what came up. The instruction generator's Bloom/DOK calibration can also be tuned per event type if the cards run too shallow or too deep for the class.

A rubric is just YAML

The default rubric is discipline-agnostic; instructors can upload their own to reshape what gets tracked, e.g. for a virology unit built around this exact CHIKV pipeline:

objectives: - id: CHIKV-1 description: "Explain why E1/E2 conservation matters for pan-genotypic binder design." bloom_level: Understand dok_level: 2 - id: CHIKV-2 description: "Interpret a molecular-docking ΔG score and cross-reactivity σ." bloom_level: Analyze dok_level: 3

Every step is a structured, gradable record

One JSON record per teaching card, appended to a per-session JSONL log:

{ "kind": "step", "event_type": "code", "step_id": 4, "title": "Query CHIKV E1-E2 structure", "bloom_target": "Apply", "dok_target": 2, "instruction": { "what": "Querying the PDB for a CHIKV trimer template.", "why": "Docking needs a structural target before anything else can run.", "prerequisites": ["PDB resolution & quality filtering"], "look_for": ["A pre-fusion trimer, resolution ≤ 4.0 Å"] }, "kb_citations": [{"source": "course_notes.pdf", "page": 12}], "ts": "2026-07-19T06:57:15" }

Schema and rubric example adapted from the project's own docs/tutor.md.
