# Biomni Documentation Review

**Date:** 2026-07-18
**Branch reviewed:** `main`
**Release state per README:** frozen as of 15 April 2025

---

## 1. What this project is

**Biomni** is a general-purpose biomedical AI agent platform from Stanford SNAP. The repository pairs a ReAct-style LLM agent (`biomni/agent/a1.py`, `react.py`) with a large library of domain-specific biomedical tools, a curated data lake (~11 GB), a know-how protocol library, an evaluation benchmark, and MCP integration. The package is published as `biomni` on PyPI and exposes both a Gradio and a Streamlit UI.

Per the latest commits and the README, the release is **frozen as of 15 April 2025** and the on-disk release may differ from the live web platform at biomni.stanford.edu.

## 3. Design intent of the system

- **ReAct agent** (`biomni/agent/a1.py`, `react.py`) with a retrieval step, self-criticism, and tool execution, plus an LLM-driven `ToolRetriever` (`biomni/model/retriever.py`) that picks tools/data/libraries per query.
- **Centralized config** (`biomni/config.py`) — env vars, runtime mutation of `default_config`, or per-agent overrides. Priority: direct params → runtime → env vars → defaults.
- **Tool layer** organized by biological subfield with paired implementations (`biomni/tool/*.py`) and declarative schemas (`biomni/tool/tool_description/*.py`) used both for retrieval and API surface.
- **Data lake + environment description** (`biomni/env_desc.py`, `biomni/env_desc_cm.py`) acting as a metadata catalog for files and software.
- **Know-How library** (`biomni/know_how/`) — auto-retrieved markdown protocols with metadata (author, license, commercial use).
- **Benchmarks** (`biomni/task/`) — `hle.py`, `lab_bench.py`, plus a `BiomniEval1` entry point covering 433 instances across 10 tasks.
- **MCP both ways** — `add_mcp()` to consume external MCP servers and `create_mcp_server()` to expose Biomni tools.
- **Multiple UIs** — Gradio (`launch_gradio_demo`) and Streamlit (`launch_streamlit_demo`).
- **Local LLM support** — recent commit ("Default to local Ollama models and add a Streamlit UI") added `ollama_utils.py` and a Streamlit entry point.
- **Biomni-R0** — a 32B Qwen-based reasoning model served via SGLang.

## 4. Gaps and missing features

### A. Documentation gaps

1. **Tutorials referenced in docs are missing.** `README.md` and `docs/mcp_integration.md` point to `tutorials/examples/add_mcp_server/` and `tutorials/examples/expose_biomni_server/`, but `tutorials/examples/` only contains `cloning.ipynb`. Either add the folders or remove the references.
2. **No tutorial for the Streamlit UI** or for **Ollama** even though the code (`ollama_utils.py`, `streamlit_app.py`) and a commit message advertise both.
3. **No tutorial for Biomni-R0** beyond a one-paragraph code snippet in the README. The SGLang command line and the dual-LLM config pattern (different LLM for agent vs DB) deserve a worked example.
4. **No tutorial for Biomni-Eval1** beyond a 4-line code snippet. No notebook, no leaderboard docs, no task-by-task description.
5. **No Know-How authoring tutorial.** README says "use this know-how as an example" and links to `know_how/single_cell_annotation.md`, but there is no template or schema reference for the metadata fields it relies on.
6. **No architecture / design doc** beyond `DETAILS.md`, and that file is stale.
7. **No CHANGELOG / release notes** despite the project explicitly calling out a frozen April 15 2025 release — anyone joining the repo has no way to learn what changed.
8. **No security doc** beyond a single paragraph in the README. The README itself flags "executes LLM-generated code with full system privileges," which deserves a standalone sandboxing/threat-model document and concrete recommendations (containers, network policy, allowlisted binaries).
9. **No API reference beyond Sphinx auto-docs.** `docs/source/index.rst` is a one-liner. The Sphinx build instructions in `building_documentation.md` are not wired into CI, and there is no published docs site link.
10. **`biomni_env/README.md` references files that don't exist** in the repo: `new_software_v005.sh` and `fixed_env.yml` are mentioned but only `setup.sh` is shipped. Same for `bio_env_py310.yml` (referenced in `known_conflicts.md` but not in `biomni_env/`).
11. **`DETAILS.md` is auto-generated and stale** — it should either be regenerated by CI on every commit or deleted, because it will continue to drift (it already does not list `ui_core.py`, `ollama_utils.py`, `config.py`, `know_how/`, new tool modules, etc.).
12. **License doc is incomplete** — `license_info.md` is included but the README's license section just cites the paper; tool-by-tool commercial-use caveats are not surfaced anywhere obvious.
13. **`.env.example` is not documented in any guide.** It exists at the repo root and is the recommended path in the README, but `docs/configuration.md` describes env vars via `BIOMNI_*` names — there is no statement that `.env.example` is the canonical source or that env var names like `LLM_SOURCE`, `OPENAI_ENDPOINT`, `AWS_*` are read directly.
14. **No troubleshooting page** beyond the small "Troubleshooting" sections in `configuration.md` and `mcp_integration.md`. Things like the known Gradio 5.x pin, the 600s default timeout, the `azure-` model prefix, and the "auto-downloads 11 GB on first run" footgun each deserve a row.
15. **No docs for the new `config.py` module** (only mentioned in README). The `default_config` object, priority order, and how it interacts with `BIOMNI_LLM` / `BIOMNI_TIMEOUT_SECONDS` env vars need a dedicated reference.

### B. Product / feature gaps

1. **Sandboxing is not implemented.** README warns about full system access; nothing in the repo (Docker, Firejail, gVisor, separate UID) provides a safer default. This is the single biggest gap relative to the project's intent of being usable by "biomedical researchers."
2. **No retries / cost controls on tool calls.** A 600s default timeout exists but there is no per-tool budget, max-steps limit, or token/cost cap surfaced in `default_config`.
3. **No observability beyond print-style logs.** No OpenTelemetry, LangSmith, or structured-log hook in `A1`; the "logging" relies on custom callback handlers (`PromptLogger`, `NodeLogger`) that aren't documented.
4. **No automated tests** in the repo. `pyproject.toml` excludes `tutorials` and the `tool.setuptools.packages.find` only excludes `test*`, but no `tests/` directory exists. The `DETAILS.md` acknowledges "testing likely manual or via notebooks."
5. **No CI configuration files are visible** (no `.github/workflows/`), so there is no automated lint/test/docs pipeline.
6. **Gradio version is pinned to 5.x** (`gradio>=5.0,<6.0`) and noted as a known issue. There is no migration plan or test matrix.
7. **Ollama support is recent and undocumented.** `ollama_utils.py` exists, but there is no setup guide, no list of recommended models, and no benchmark of which tasks work well locally vs which need a frontier model.
8. **Data lake download is opaque.** A 11 GB first-run download is referenced but `data_lake_dict` is just a Python dict — there is no resumable/verifiable downloader, no SHA manifest visible to users, and no progress reporting.
9. **Know-How is not searchable or browsable** from any UI. Only retrievable through the agent; no static index page, no category listing, no API endpoint.
10. **Benchmarks are limited.** Only `hle.py` and `lab_bench.py` exist as in-tree tasks; the readme-promised `BiomniEval1` is loaded from HuggingFace with no in-repo runner script and no leaderboard output format.
11. **Tool descriptions and implementations can drift.** The contributor flow says to author both, but there's no CI check that every entry in `tool_description/*.py` has a matching implementation, or vice versa.
12. **No first-class streaming of agent output** in either Gradio or Streamlit examples — the README shows only a blocking `agent.go("…")` call.
13. **No caching layer** for database query results, repeated tool calls, or compiled know-how retrieval — every run re-pays the LLM/tool cost.
14. **License hygiene is not enforced.** README says "Review each component carefully before commercial use" but there is no machine-readable license metadata per tool.
15. **No migration path from E1 → E2.** The README calls for community help to build E2, but there's no spec, no RFC, no roadmap document, and no labeled-issues workflow visible in the repo.

## 5. Recommended next steps (prioritized)

1. **Add a `CHANGELOG.md` and a `docs/architecture.md`** to replace the stale `DETAILS.md`.
2. **Remove or regenerate** `DETAILS.md` so it doesn't mislead.
3. **Fix the broken documentation links** (the missing `tutorials/examples/*` folders and the `new_software_v005.sh` / `fixed_env.yml` / `bio_env_py310.yml` references).
4. **Ship the promised tutorials**: MCP add/expose, Streamlit, Ollama, Biomni-R0, Biomni-Eval1, Know-How authoring.
5. **Add a sandboxing guide + a minimal Docker recipe** — this is the highest-impact safety improvement.
6. **Add a `tests/` directory and a GitHub Actions workflow** running ruff + a small smoke test for `A1(...)` instantiation.
7. **Surface cost/step controls** (`max_steps`, `max_cost_usd`, `tool_timeout`) in `default_config` and document them.
8. **Add CI checks** that every tool description has an implementation and every implementation is described.
9. **Document `config.py` / `default_config`** as the canonical configuration entry point, replacing the duplicate env-var prose scattered across `README.md` and `docs/configuration.md`.
10. **Publish the Sphinx site** (currently only `make html` is documented) and link it from the README.
